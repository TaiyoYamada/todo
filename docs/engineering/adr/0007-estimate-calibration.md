# 0007 着手リミットを、本人の実績から自動で前倒しする

- 日付: 2026-10-09
- 状態: 採用(Claude が決めた。オーナーの確認待ち)

## 状況

タスクは「締切 − 見積もり」の時刻(着手リミット)を過ぎるとロックの理由になります。

市場調査のあとの見直しで、ここに一番大きな穴があると分かりました([批評と強化案](../../research/critique-and-ideas.md))。人は所要時間を短く見積もります(計画錯誤)。見積もりどおりの時刻にロックしても、そこから始めたのでは間に合いません。アプリに従って締切を落とすと、責められるのはアプリです。

それまでの仕様は、倍率の初期値が 1.0 で、上げるかどうかは利用者に任せていました。見積もりが甘い人ほど自分の見積もりを疑わないので、初期値のまま使われると考えられます。

## 決定

- 着手リミットは「締切 −(見積もり × 倍率)」で計算する。
- 倍率の決め方は、設定の初期値を「自動」にする。固定(1 / 1.25 / 1.5 / 2 倍)も選べる。
- タスクを完了にするとき、実際にかかった時間を1問だけ聞く。選択肢は見積もりの 0.5 / 1 / 1.5 / 2 / 3 倍(5 分刻みに丸める)。
- 「自動」の倍率は `EstimateCalibration` が決める。

| 項目 | 値 |
|---|---|
| 使う実績 | 完了済みで、実際の時間に答えたタスクの「実際 ÷ 見積もり」 |
| 見る範囲 | 完了が新しい順に 10 件 |
| 代表値 | 中央値 |
| 実績が 3 件に満たない間 | 1.5 倍 |
| 範囲 | 1.0〜3.0 倍に収める |

## 理由

- 自動を初期値にするのは、設定を開かない人にこそ効かせるため。
- 平均ではなく中央値を使うのは、1回だけ大きく外したタスクに振り回されないため。
- 直近 10 件に絞るのは、古い癖に引きずられないため。
- 下限を 1.0 にするのは、見積もりより早く終わる人でも、着手リミットを後ろへはずらさないため。間に合わない側に倒さない。
- 上限を 3.0 にするのは、入力の間違いや特殊な1件で、ロックが極端に早まるのを防ぐため。
- 完了時の質問は、完了の確認を兼ねる。完了は自己申告なので、押すだけで外れるのは避けられない。そこに1問を挟み、答えを学習に使う。
- 実績は端末の中の、その人だけのデータになる。機能は真似できても、積み上がった実績は真似できない。

## 検討した代替案

| 案 | 採らなかった理由 |
|---|---|
| 倍率を固定の 1.5 に上げるだけ | 人によって癖が違う。早く終わる人には厳しすぎ、もっと甘い人には足りない |
| 集中の計測のように、タスクの作業時間を計る | 正確だが、タスクにも計測の操作が要る。入力の手間を増やさないことを優先した。将来の案として残す |
| 実績の平均を使う | 外れ値に弱い |
| タスクの種類ごとに倍率を持つ | 種類の入力が要る。実績が種類ごとに割れて、学習が遅くなる |

## 影響

- 1.5 倍という初期値の根拠は弱い。「見積もりは 1.5 倍前後かかるとされる」という一般論で、このアプリの利用者で確かめた値ではない。
- 答えは自己申告で、選択肢は粗い。倍率は目安にとどまる。
- タスクを1つ完了すると倍率が変わり、**ほかの未完了のタスクの着手リミットも動く。** 予報が急に早まることがある。
- 振り返りの「ロックの前に完了 / 後に完了」は、いまの倍率で計算し直して数える。倍率が変わると過去の分類も変わる。
- 完了を取り消す(未完了に戻す)と、実際の時間も消え、学習からも外れる。
- 設定の画面と、タスクの編集画面に、いまの倍率を表示している。黙って変わる値にしない。
- 計算は `Domain` にあり、テストがある(`EstimateCalibrationTests`)。
