# 0001 アーキテクチャに TCA を使う

- 日付: 2026-10-09
- 状態: 採用(Claude が決めた。オーナーの確認待ち)

## 状況

このアプリは、時刻と保存データからロックの状態を決めます。判定を間違えると、ロックが外れない、または掛からないという一番困る不具合になります。

状態を変える要因が多くあります。利用者の操作、保存データの変更、時間の経過、アプリが前面に戻ること、スクリーンタイムの許可です。これらを画面ごとにばらばらに扱うと、どこで状態が変わったのかを追えなくなります。

また、実際のロックはシミュレータで確かめられません。時刻、DB、ロックを差し替えてテストできる形が必要です。

## 決定

The Composable Architecture(TCA)1.26 を使います。

- 状態の変更は Reducer に集める。View は状態を描き、操作をアクションとして送るだけにする。
- 外の世界(時刻、ID、DB、ロック、時計)には `@Dependency` を通して触る。Reducer の中で `Date()` や `UUID()` を直接呼ばない。
- 画面の出し分けは `@Presents` と `@Reducer enum Destination` で表す。
- 画面をまたぐ共有は `@Shared` を使う([0004](0004-shared-board-state.md))。

## 理由

- 依存を差し替えれば、時刻を固定して Reducer をテストできる。「着手リミットを過ぎたらロック」のような時間の絡む動きを、実際に待たずに確かめられる。
- 副作用(DB への書き込み、時計の待ち、ロックへの反映)が `Effect` として戻り値に現れる。どのアクションが何を起こすかをコードで追える。
- 待ちの取り消し(`cancellable`)が標準で用意されている。次に状態が変わる時刻まで待つ処理を、状態が変わるたびに張り直すのに使っている。
- 見本データへの切り替えが、`Store` を作るときに `database` を差し替えるだけで済む。

## 検討した代替案

| 案 | 採らなかった理由 |
|---|---|
| SwiftUI の `@Observable` だけで組む | 依存の少なさは利点。ただし、時刻や DB の差し替えと、副作用の扱いを自分で決めて守り続ける必要がある。1人での開発で、その規律をテストなしに保つのは難しいと判断した |
| MVVM + 自前の依存注入 | 上と同じ。TCA が用意しているものを作り直すことになる |

## 影響

- マクロ(`@Reducer`、`@ObservableState`、`@DependencyClient`)に頼るので、ビルドが遅くなる。コマンドラインからのビルドでは、マクロの承認を飛ばす指定(`-skipMacroValidation`)が要る。
- TCA の更新に追従する手間がある。大きな版の更新は、この文書を更新してから行う。
- Reducer のテストはまだ書いていない(置き場だけある)。この決定の利点は、テストを書いて初めて得られる。
- 外すときの退路: 判定と計算は `Domain` にあり、TCA に依存していない。作り直すのは `AppFeature` の Reducer と、View の結線だけで済む。
