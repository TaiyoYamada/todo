# 0004 全画面が1つの Board を共有し、書くのは AppFeature だけにする

- 日付: 2026-10-09
- 状態: 採用(Claude が決めた。オーナーの確認待ち)

## 状況

ほとんどの画面が、同じものを必要とします。

- 「今日」は、余裕、ロック予報、今日の分、締切。
- 「予定」は、目標とタスクの一覧と、それぞれの着手リミット。
- 「振り返り」は、記録の集計と見積もりの癖。
- 集中、タスクの編集、設定も、いまのロックの状態や倍率を見る。

画面ごとに DB を読み、画面ごとにロックの状態を計算すると、同じ瞬間に画面どうしで違う答えを出すおそれがあります。たとえば「今日」はロック中なのに、「予定」ではまだ余裕がある、という表示です。

## 決定

- 保存データの全体を `World` という1つの値にする。
- `World` と、そこから計算した `LockStatus`、読み込み済みかどうかを `Board` にまとめる。
- `Board` は TCA の `@Shared(.inMemory("board"))` で共有する。
- **書くのは `AppFeature` だけ**(`@Shared`)。ほかの画面は読むだけ(`@SharedReader`)。
- 画面が保存データを変えたいときは、`Board` ではなく `DatabaseClient` に書く。変更は DB の監視を通って `AppFeature` に戻り、`Board` に反映される。
- ロックの状態を計算するのは `AppFeature` の `refresh` の1か所だけ。

## 理由

- 状態の出どころが1か所なので、画面どうしの食い違いが起きない。
- 「DB に書く → 監視で戻る → 計算し直す」という一方向の流れになる。画面が自分で状態を書き換えて、DB とずれることがない。
- 読むだけの型(`@SharedReader`)にしておくと、子の画面が誤って書くコードはコンパイルできない。
- 子の画面に `World` や `LockStatus` を引数で配り直す必要がない。画面を足すのが軽い。
- データ量が小さいので、丸ごと持っても負担にならない。

## 検討した代替案

| 案 | 採らなかった理由 |
|---|---|
| 親から子へ、必要な値を状態として渡す | 値が変わるたびに、親がすべての子の状態を書き換えるコードが要る。画面が増えるほど漏れやすい |
| 画面ごとに DB を監視する | 計算が画面の数だけ走り、同じ瞬間の答えがそろう保証がない |
| `LockStatus` を DB に保存する | 時刻で変わる値なので、保存した瞬間から古くなる。計算で出せるものは保存しない |

## 影響

- `Board` はメモリ上だけにある。起動のたびに DB から読み直す。読み終えるまでは `isLoaded` が false で、画面は背景だけを出す。
- 子の画面を単独でテストやプレビューするときは、先に `Board` に値を入れる必要がある。
- `LockStatus` は時刻で古くなる。`AppFeature` が、次に状態が変わる時刻と 15 秒ごとに計算し直す([設計](../architecture.md) 2.3)。子の画面は `board.status.now` を「いま」として使う。
- 記録が増えて `World` が大きくなったら、`Board` に載せる範囲を絞る。その場合も、書くのは `AppFeature` だけという約束は変えない。
- 拡張機能は `Board` を読めない(別のプロセス)。代わりに写しを読む([0005](0005-screen-time-boundary.md))。
