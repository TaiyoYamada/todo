# 0002 永続化に SQLiteData を使い、監視は GRDB を直接使う

- 日付: 2026-10-09
- 状態: 採用(Claude が決めた。オーナーの確認待ち)

## 状況

保存するものは、目標、タスク、集中の記録、パスの記録、設定です。件数は小さく、端末内だけに保存します([仕様](../../product/spec.md) 7)。

求めることは3つです。

- 保存データが変わったら、ロックの状態をすぐ計算し直せること。
- 表の形を、配布後も安全に変えられること(移行)。
- テストで、実際の DB に対して読み書きを確かめられること。

## 決定

- SQLiteData 1.12 を使う。行の型は `@Table` で定義し、読み書きは型のついたクエリで書く。
- 表の定義と移行は、SQL の文字列で書く(`#sql`)。
- 変更の監視は、SQLiteData の土台である GRDB の `ValueObservation` を直接使う。
- これらは `DatabaseClient` の中に閉じ込める。外に出るのは `Domain` の型と `AsyncStream<World>` だけ。

## 理由

- SQLite は中身を直接見られ、移行を SQL で書ける。SwiftData より挙動を追いやすい。
- 型のついたクエリで、列名の打ち間違いをコンパイル時に見つけられる。
- 監視に `ValueObservation` を直接使うのは、保存データ全体(`World`)を1つの流れとして `DatabaseClient` から出したいから。SQLiteData の `@FetchAll` などは View や機能の中に置くもので、DB を境界の内側に閉じ込める形と合わない。
- 移行を SQL の文字列で書くのは、一度配布した移行を、行の型の変更に引きずられない形で固定するため。
- テストでは、テストごとの一時データベースが使われる。本番のデータに触れずに、実際の SQLite で確かめられる。

## 検討した代替案

| 案 | 採らなかった理由 |
|---|---|
| SwiftData | 移行と監視の挙動を細かく制御しにくい。TCA の Reducer から使うには、結局は境界の型を挟むことになる |
| GRDB だけを使う | 十分に成り立つ。行の型とクエリを自分で書く量が増えるだけ。SQLiteData で困ったときの退路として残す |
| UserDefaults や JSON ファイル | 集中の記録が増えていくので、絞り込みと部分的な更新ができない形は避けた |

## 影響

- `Schema.swift` は SQLiteData だけを、`Observation.swift` は GRDB だけを import する。両方に `Table` や `Column` という名前があり、同じファイルで読み込むと衝突するため。
- GRDB を `Package.swift` に明示している。SQLiteData が GRDB の版を上げたときに、食い違いに注意する。
- 設定(`Preferences`)は JSON にして1列に入れている。項目を足しても移行が要らない代わりに、SQL から中身を絞り込めない。
- 変更のたびに `World` を丸ごと読み直す。記録が増えたら、読む範囲を絞る必要がある。
- 拡張機能は DB を開かない([0005](0005-screen-time-boundary.md))。DB のファイルを App Group に置く必要はない。
- iCloud 同期は未検討。SQLiteData には CloudKit と同期する仕組みがあるが、このアプリの表で使えるかは確かめていない。
- 退路: GRDB だけに切り替える場合、書き直すのは `DatabaseClient` の中(`Schema.swift`)だけ。DB のファイルと表はそのまま使える。
