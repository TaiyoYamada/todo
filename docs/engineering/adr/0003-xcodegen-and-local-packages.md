# 0003 XcodeGen と、2つのローカルパッケージで構成する

- 日付: 2026-10-09
- 状態: 採用(Claude が決めた。オーナーの確認待ち)

## 状況

決めることは3つです。

- Xcode のプロジェクトファイルを、どう管理するか。
- コードを、どの単位で分けるか。
- 開発用と本番用のビルドを、どう分けるか。

拡張機能(スクリーンタイム、ウィジェット)を足す予定があり、ターゲットは増えます。

## 決定

- `Todo.xcodeproj` は XcodeGen で `project.yml` から生成し、コミットしない。依存の版を固定する `Package.resolved` だけはコミットする。
- コードは2つのローカルパッケージに置く。アプリ本体(`App/`)には起動の1ファイルだけを置く。
  - `Packages/Domain`: Foundation だけに依存する純粋なロジック。iOS と macOS の両方でビルドできる。
  - `Packages/TodoKit`: 画面、保存、ロックの境界、部品。iOS 専用。
- 画面は、当面すべて `AppFeature` という1つのターゲットに置く。フォルダで分ける。
- 構成は Dev と Prod の2系統にし、違いは `Configs/*.xcconfig` に書く。スキームは `Todo-Dev` と `Todo-Prod`。

## 理由

- プロジェクトファイルを生成物にすると、差分が読める YAML になり、マージの衝突が起きない。ターゲットを足すのも数行で済む。
- `Domain` を別パッケージにすると、`swift test` を macOS 上で回せる。シミュレータを起動しないので速い。ロックの判定のテストを、気軽に何度も回せることを優先した。
- `Domain` が Foundation 以外に依存できないことを、パッケージの境界で守れる。
- 画面を機能ごとのターゲットに分けないのは、まだ画面が少なく、分けても得るものが少ないから。分けると、共有する型(`Board`、`Route`)の置き場と、文言カタログの分割を先に決める必要がある。
- Dev と Prod で識別子を変えると、開発中の版と公開した版を同じ端末に入れられる。

## 検討した代替案

| 案 | 採らなかった理由 |
|---|---|
| `Todo.xcodeproj` をそのままコミットする | 差分が読めず、ブランチをまたぐと衝突しやすい |
| Tuist | できることは多いが、この規模では XcodeGen の YAML で足りる |
| パッケージを1つにまとめる | `Domain` を macOS でテストするには、パッケージ全体が macOS でビルドできる必要がある。TCA や SwiftUI の画面を巻き込みたくない |
| 最初から機能ごとにターゲットを分ける | 上の「理由」のとおり。必要になってから分ける |

## 影響

- ファイルを足したり消したりしたら、`make bootstrap` をやり直す。
- 構成の名前は `Debug-Dev` のように `Debug` / `Release` で始める。Xcode が、ローカルパッケージをどちらでビルドするかを構成の種類から決めるため。
- `DEV` というコンパイル条件は、アプリ本体のターゲットにだけ付く。パッケージの中では使えない。見本データへの切り替えは、アプリ本体が起動引数を読んで `RootView` に渡す形にしている。
- 拡張機能を足すときは `project.yml` にターゲットを足し、`SharedCore` と `Domain` だけに依存させる。
- `AppFeature` を分けるきっかけの目安: ビルドが目に見えて遅くなったとき、または拡張機能と画面の一部を共有したくなったとき。
