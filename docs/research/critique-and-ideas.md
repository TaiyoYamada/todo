# 批評と強化案（名称の検討を含む）

調査日: 2026-10-09

## 結論

1. **差別化は「ある」が薄い。** 新しいのは「締め切り − 所要時間からの自動ロック」と「ロックまでの余裕を主画面にする」の組み合わせだけで、技術的な障壁ではなく見せ方の新しさにとどまる。毎日ノルマのロックは既に多数ある（competitors.md）。
2. **中核の仕組みに論理的な穴がある。** 「これ以上遅らせると間に合わない時点」でロックしても、見積もりが少しでも甘ければ間に合わない。人は所要時間を系統的に短く見積もる。
3. **予報は「まだ遊べる」の許可証にもなる。** 売りの UI が、先延ばしを締め切り直前まで正当化する方向に働く可能性がある。
4. **「計画の手間ほぼゼロ」と「タスクごとに締め切りと所要時間を入れる」は両立していない。** 入力の自動化がないと、対象の利用者は最初の数件で入力をやめる。
5. **「Yoyu」は使えない可能性が高い。** 日本の App Store に同名・同音のアプリが3本あり、うち1本は同じ仕事効率化カテゴリで「残りの余裕を表示する」発想まで近い。

このまま作ると「TodoLock やあとスマと同じものに、締め切り機能が付いたアプリ」と受け取られる。下の強化案 1〜3 を入れて初めて、別物として説明できる。

## 差別化の評価

| 要素 | 新規性 | 守れるか | 根拠 |
|---|---|---|---|
| 毎日ノルマが終わるまでロック | なし | — | [TodoLock](https://apps.apple.com/jp/app/id6760632571)、[あとスマ](https://apps.apple.com/jp/app/id6782053907)、[Unrot](https://apps.apple.com/us/app/id6746537171) ほか |
| 締め切り − 所要時間からの自動ロック | 見つからず | 守れない。計算は引き算ひとつ | 近い例は [Proc](https://theprocapp.com/)、[Structured × one sec](https://tutorials.one-sec.app/en/articles/3035010)、[Finiti](https://apps.apple.com/app/id6761764736) |
| ロック予報を主画面・ウィジェットに | 見つからず | UI は真似できる。先に名前と結びつけば多少は守れる | 近い例は [Finiti](https://apps.apple.com/app/id6761764736) のロック画面カウントダウン |
| 緊急パス 15分 | なし | — | [TaskLock](https://apps.apple.com/us/app/id6792368867) が同じ仕様 |
| 「ドパガキ」向けという訴求 | なし | — | [あとスマ](https://apps.apple.com/jp/app/id6782053907)、[ドパロック](https://apps.apple.com/jp/app/id6774131105) |

利用者が毎日触れるのは「毎日ノルマ」の側で、ここは既存アプリと同じ体験になる。新しい部分（締め切りロック）が働くのは締め切りがある日だけ。日常の体験の大半が既出、という構造になっている。

## 設計上の弱点

### 1. 見積もりは外れる

計画錯誤の研究（Buehler, Griffin, Ross 1994）では、卒業論文の完成までの日数を学生に予測させたところ、平均予測 33.9日に対し実際は 55.5日で、予測どおりに終えたのは約3割だった（[Wikipedia の要約](https://en.wikipedia.org/wiki/Planning_fallacy)。原論文の全文は未確認、[論文 PDF](https://bear.warrington.ufl.edu/brenner/mar7588/Papers/buehler-et-al-1994.pdf)）。「最悪の場合」の予測ですら実績より短かった。

「締め切り − 見積もり」でロックするなら、見積もりが実際の6割しかない利用者は、アプリに従っても締め切りを落とす。そのとき責められるのはアプリになる。

現行の[仕様](../product/spec.md)（3.2）には余裕係数があるが、初期値は 1.0（所要時間ちょうど）で、1.25 や 1.5 に上げるかは利用者に任されている。見積もりが甘い人ほど自分の見積もりを疑わないので、初期値のまま使われると考えるべき。

### 2. ロックしても作業は始まらない

ロックが保証するのは「選んだアプリが開けない」ことだけ。ブラウザ、別の端末、ゲーム機、漫画、睡眠への逃避は止められない（risks.md）。利用上限を自分で設定できるようにすると SNS 利用が減ることは実験で示されているが（[Allcott, Gentzkow, Song](https://www.nber.org/papers/w28936)）、減った時間が課題に向かうことまでは示されていない。

### 3. 予報が先延ばしを正当化する

「余裕 あと3時間」は「あと3時間は遊んでよい」とも読める。締め切りの手前に自分で期限を置く効果についても、証拠は固くない。Ariely と Wertenbroch（2002）は自分で決めた締め切りに一定の効果を報告したが、2025年の追試は再現できなかったとしている（[追試の草稿](https://bpb-us-e1.wpmucdn.com/wp.nyu.edu/dist/c/16384/files/2025/09/Ariely_Replication-1.pdf)。査読状況は未確認）。

予報が「ロック前に動く」行動を生むかどうかは、このアプリの成否を決める仮説で、まだ誰も確かめていない。

### 4. 入力の手間

締め切りタスクには期限と所要時間の入力が要る。競合は取り込みで手間を減らしている。Proc は Canvas から課題を取り込み（[出典](https://theprocapp.com/)）、TodoLock は Apple リマインダーと同期し（[出典](https://apps.apple.com/jp/app/id6760632571)）、TaskLock は Apple カレンダーと同期する（[出典](https://apps.apple.com/jp/app/id6760604253)）。手入力だけでは見劣りする。現行の[仕様](../product/spec.md)（8）はカレンダー連携と学習管理システム連携を「今は入れないもの」に置いているが、少なくともリマインダーからの取り込みは初版に入れる価値がある。

### 5. 完了は自己申告

「完了」を押せば解除される（[仕様](../product/spec.md) 3.5 も未対策と認めている）。競合は写真の AI 判定や提出物の採点で対抗している（competitors.md）。正直な利用者しか守れないという割り切りは可能だが、対象を「意志で止められない人」と置くなら矛盾を抱える。

### 6. 緊急パスの長さ

仕様は1回15分、週2回を初期値にしている。15分では、連絡や調べものには足りても、ロック対象のアプリで用事を済ませるには短いことが多い。足りないと感じた利用者は設定から許可を切るか、アプリを消す。競合の例は「1日1回15分」（[TaskLock](https://apps.apple.com/us/app/id6792368867)）と「1日10分」（[Finiti](https://apps.apple.com/app/id6761764736)）で、週2回はそれより厳しい。

## 欲しがらない人

| 層 | 理由 |
|---|---|
| 締め切りや明確な目標がない人 | ロックの条件になるものがない。「ドパガキ」と呼ばれる層の相当部分がここに入ると考えられる（推測） |
| 時間が溶ける先がゲーム機や PC の人 | Screen Time API はその iPhone にしか効かない |
| Android 利用者 | 日本全体で 54.1%（[MMD研究所調査](https://selectra.jp/telecom/news/iphone-share-202608)） |
| 娯楽アプリが連絡手段でもある人 | Instagram や Discord をロックすると、友人やサークルとの連絡も止まる |
| 保護者に端末を管理されている高校生 | 本人の認可で動くか未確認（risks.md） |
| 絶対に解除できないロックを求める人 | 物理デバイスの [Brick](https://getbrick.com/products/brick) や、解除不能モードを持つ [Blockin](https://apps.apple.com/jp/app/id1659162950) に向かう |
| 既に予定を細かく組んでいる人 | Structured と one sec の無料連携で足りる（[出典](https://one-sec.app/integrations/structured/)） |
| 子どもを制限したい保護者 | 必要なのは保護者側から設定できる仕組みで、別の製品になる |
| お金を払う気のない学生 | 利用はしても売上にならない。Opal は無料化で転換率が半分以下になった（[RevenueCat](https://www.revenuecat.com/blog/growth/kenneth-schlenker-sub-club-podcast-2026)） |

逆に最も合うのは、締め切りと作業量が自分で分かっていて、端末が自分の管理下にある人。大学生のレポート・課題、院試や TOEIC や資格の受験者、社会人の資格学習者がこれにあたる。「ドパガキ全般」より狭いが、支払い能力と継続理由がある。

## 強化案

### 1. 見積もりの自動補正を中核にする（製品）

- 余裕係数の初期値を 1.0 から 1.5 に上げる（現行仕様では 1.5 は選択肢の上限）。
- タスクごとに実際にかかった時間を記録し、「あなたの見積もりは平均で1.6倍かかる」のような個人係数を出して、次回のロック時刻に反映する。
- 効果: 弱点1に直接答える。使うほど正確になるので、乗り換えにくさが生まれる。競合が機能を真似ても、個人の実績データは真似できない。
- 予報の表示も「余裕 3時間」ではなく「あなたの実績だと余裕 1時間40分」と出せる。弱点3の「まだ遊べる」を弱める方向に働く。

### 2. 二段階ロックにする（UX）

- 余裕が残り少なくなった段階（例: 所要時間の2倍を切ったら）で、対象アプリを開くたびに数秒待たせる。余裕がゼロになったら完全にロックする。
- 待たせるだけの介入でも利用が減ることは、one sec の共同研究で報告されている（最初の6週間で 57% 減、[研究一覧](https://one-sec.app/max-planck-study)）。
- 効果: 「いきなり締め出される」体験を避けつつ、ロック前に動くきっかけを作る。予報だけでは動かない利用者への中間の手段になる。

### 3. 入力をなくす（製品）

- Apple のリマインダーとカレンダーから、期限つきの項目を取り込む。競合が既にやっている最低線。
- 大学の学習管理システムからの取り込み。Proc は Canvas に対応している。日本の大学で使われるシステムで同じことができるかは未調査。
- 試験日のプリセット（TOEIC、共通テスト、主要資格）を用意し、長期目標は「試験を選ぶ → 1日の分数を選ぶ」の2操作で作れるようにする。
- 所要時間は入力させず、種類（レポート、問題集、暗記）と量から初期値を出し、強化案1の補正で合わせていく。

### 4. 「完了」ではなく「着手」で扱いを変える（UX）

- ロックがかかった時点で「今から始める」を押すと作業タイマーが動き、所要時間ぶん進めたら完了を押せるようにする。作業時間がゼロのまま完了は押せない。
- 効果: 弱点2と5に同時に答える。ロックが罰ではなく作業開始の合図になる。完全な不正防止ではないが、1タップでの解除はなくなる。
- 同じ仕組みで強化案1の実績時間が自動で取れる。

### 5. 予報だけの版を先に出す（成長と検証）

- ロックなしで「次のロック相当時刻までの余裕」をウィジェットに出すだけのアプリは、Family Controls を使わないので、エンタイトルメントの承認を待たずに出せる。
- 効果: 承認待ちの期間（risks.md）を無駄にしない。予報だけで行動が変わるかという中心仮説を、最も安く確かめられる。名前と「ロック予報」という言葉を先に取れる。
- 測るもの: ウィジェット設置率、7日後の継続、予報が赤になってから着手するまでの時間。

### 補足: 広げ方

- 学生は無料で使える範囲を広く取る。Opal は無料利用者が増えたことが成長の原動力になったと説明している（[RevenueCat](https://www.revenuecat.com/blog/growth/kenneth-schlenker-sub-club-podcast-2026)）。
- 最初から英語版を出す。米国の上位ブロッカーは評価5万件超が少なくとも5本あり、日本の上位（1〜2万件）より1桁大きい（market-and-demand.md）。
- 「ドパガキ対策」を看板にしない。先行2本と並ぶと後発に見える。「締め切りから逆算してロックする」「ロック予報」を看板にする。
- 友人同士で互いの余裕が見える機能は、既存の [CoLock](https://apps.apple.com/jp/app/id6754523922)（友人と制限状況を共有）と Opal のランキングが示す方向で、共有される画面が獲得経路になる。ただしサーバーが必要になり、端末内完結の利点を失う。初版では見送り、予報の画像を共有できる程度にとどめるのが妥当。

## 名称

**ここでの確認は App Store 検索 API とウェブ検索による簡易なもので、商標の法的な調査ではない。** 特許庁の J-PlatPat は今回検索していない。出願・公開の前に、商標の専門家による確認が必要。

### 「Yoyu」の状況

| アプリ | 開発者 | カテゴリ | 公開 | 内容 |
|---|---|---|---|---|
| [Yoyu 出発判断タイマー](https://apps.apple.com/jp/app/id6778750422) | 個人 | 仕事効率化 | 2026-06 | 目標時刻と移動時間から出発の限界を計算し、残り時間と余裕を色で表示 |
| [YOYU](https://apps.apple.com/jp/app/id6794309370) | 個人 | ファイナンス | 2026-08 | 夫婦・カップル向け家計簿。「今月の余裕」をホームに大きく表示 |
| [ヨユウ](https://apps.apple.com/jp/app/id6763001725) | 個人 | ヘルスケア | 2026-06 | 6項目を選んで「余裕度」を記録するセルフケアアプリ |

- 3本とも評価は0〜1件で、著名とは言えない。ただし「YOYU」という完全一致の名称が既に使われている。
- App Store Connect は使用中のアプリ名を拒否することがある。他の開発者の名称と重複した場合の扱いは資料によって説明が分かれ（[開発者フォーラム](https://developer.apple.com/forums/thread/691494)）、「Yoyu」単独で登録できるかは、実際にアプリレコードを作って試すまで分からない（未確認）。
- 「Yoyu 出発判断タイマー」は同じカテゴリで、「限界の時刻までの残りを見せる」という発想がこちらの予報と重なる。検索結果で並んだときに混同される。
- ウェブ検索では「Yoyu」「ヨユウ」の登録商標は見つからなかった。検索エンジンは商標データベースの中身を拾えないので、これは「ない」ことの確認にはならない。
- ガイドライン 5.2.1 と 4.1(c) は、他者の名称やブランドを無断で使うことを禁じている（[App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)）。
- 英語圏では意味が伝わらず、「yo-yo」と聞き間違えられやすい（意見）。

以上から、「Yoyu」単独の名称は避けることを勧める。

### 代替案

日米の App Store で同名アプリを検索し、完全一致が見つからなかったものを挙げる（2026-10-09 時点、iTunes Search API。検索漏れはありうる）。

| 候補 | 表記 | 理由 | 懸念 |
|---|---|---|---|
| Lockcast | ロックキャスト | lock + forecast。中心機能の「ロック予報」をそのまま名前にできる。英語圏でも通じる | 「cast」から配信や Podcast を連想される。他業種での使用は未確認 |
| Sakiyari | サキヤリ（先やり） | 「先にやる」。競合の「あとスマ」と対になる行動の言葉で、覚えやすい | 英語では意味が伝わらない |
| Girimae | ギリ前 | 「ギリギリになる前に」。締め切り逆算ロックの考え方を、対象層の言葉で言える | 軽い印象。社会人の資格学習者には合わない可能性 |
| Shimemae | シメマエ（締め前） | 「締め切り前」。何のアプリかが日本語で一度に伝わる | 語感が硬い。長期目標の側面が名前に出ない |
| YoyuLock | ヨユウロック | 「余裕」の発想を残しつつ、文字列として既存3本と区別できる。検索語「ロック」を含む | 既存の Yoyu 系と並ぶと派生品に見える。混同の懸念は完全には消えない |

検討して外したもの: Leeway（[Leeway: Time Budget Planner](https://apps.apple.com/us/app/id6779352711) が仕事効率化に存在）、Nokori（家計簿を中心に同名が多数）、Yohaku（同名が5本以上）、Headroom（同名が複数）、Atode（タスク管理に同名が複数）。

推奨は Lockcast。日本語と英語の両方で使え、製品の独自点を名前が説明する。日本語の副題に「締め切りから逆算してロック」を付ければ、検索語も確保できる。
